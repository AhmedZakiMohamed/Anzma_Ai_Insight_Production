# v0.2 G1 Working Slice — Static Review Findings

**Review date:** 25 November 2026  
**Reviewed revision:** working tree based on `main` at `58511df37d1836ccb804f92ad012f8401495c02b`  
**Review type:** source and documentation inspection only; no commands, tests, or runtime checks were used to verify behavior in this review.  
**Disposition:** useful synthetic engineering proof; not ready for product acceptance or customer-production claims.

This review separates findings about the current slice from requirements for the larger product. The two operational questions are acceptance examples for reusable capabilities; they are not a product boundary.

## Findings

| Priority | Finding | Evidence and impact | Closure evidence |
|---|---|---|---|
| **P1 — product architecture** | Analytics execution is a fixed two-operation endpoint, not a reusable catalog-driven capability service. | `app/api/analytics_api.py` constrains `analysis` to `doors.after_hours` and `devices.offline_frequency`, then dispatches with a branch. This proves two typed analyses, not the broad operational question capability in the CEO direction. Adding each case as another special chat/API branch will not meet the product goal. | Approved versioned analytic definition and registry/tool contract; add an independent analytic using the same authorization, prerequisite, execution, evidence, coverage and result path without a question-specific chat branch. |
| **P1 — onboarding/product gate** | The reference integration is an engineer-operated historical backfill, not guided customer self-service. | `connectors/reference_rest/connector.py` reads fixed environment variables and explicit time bounds, and its README requires existing source and external-asset mappings. The manifest advertises only `history.events`. There is no customer setup/discovery/mapping workflow in this slice. | Customer-like install and browser setup walkthrough that registers a source, verifies scoped access, discovers available data, resolves mappings and starts sync without source-code or SQL edits. |
| **P1 — release packaging** | The G1 source/connector are not orchestrated by the repository's main installation stack. | `deploy/compose/docker-compose.yml` defines DB, Ollama, API and optional freshness services only. The reference REST Dockerfile exists, but no reference-service or connector-runner service consumes it. Fresh-volume SQL mounts stop at 012; `scripts/apply_migrations.py` can discover 013–014 and later migrations, but the main Compose startup does not run that path. This leaves a gap between fresh installation, upgrade and G1 demonstration packaging. | Define and rehearse a single versioned install/upgrade path that applies every intended migration and starts/configures the connector runtime without exposing secrets. Verify the clean install and upgrade paths converge on the same schema and supported services. |
| **P1 — trust/reproducibility** | The returned result identifier does not identify a retained result snapshot, and completeness is always unknown. | `app/services/analytics/operational.py` generates a random `result_id` per execution and returns `completeness: UNKNOWN`; connector synchronization state is not retained in Core. Results cannot yet be reconstructed or used as a durable common reference for chat, dashboards and reports. | Persisted result or reproducible execution record (operation/version/parameters/data watermark), plus durable per-source sync/checkpoint/completeness state; prove a partial or missing page remains visible as partial/unknown. |
| **P1 — sensitive-action policy** | Current alert explanation behavior does not match the user's earlier preference for deterministic action selection on sensitive alerts. | `app/domain/ai/explanation.py` passes eligible causes/actions to the model and accepts model-selected IDs; when no action ID is selected, it returns all eligible actions. `app/domain/ai/recommendations.py` includes provisional and approved actions, while playbook defaults are provisional. The CEO materials do not settle this model authority question, so ADR-11 is open. | Obtain product/operations approval for the authority policy; if option A in ADR-11 is selected, prove the action is selected deterministically from an approved playbook independent of model output/failure and provisional actions are never labeled approved. |
| **P2 — capacity consistency** | The two analyses have different result-volume controls. | `doors_after_hours` fetches at most 10,001 records and marks a 10,000-row truncation. `offline_frequency` reads every transition in the requested window into process memory, builds all evidence arrays and has no comparable result cap or truncation signal. At a high-event site this can consume disproportionate database, memory and response resources. | Define per-operation and shared query budgets (time window, scanned rows, output rows, evidence size); enforce them in SQL/service and report truncation without claiming an exact total when the total is unknown. |
| **P2 — request usability** | Chat date handling remains a narrow technical interface. | The G1 record says recognized chat intents require two explicit `YYYY-MM-DD` dates; the typed endpoint requires `start_date` and `end_date`. Normal date phrases, missing/ambiguous dates, timezone context and follow-up clarification are not evidenced as a generalized resolver. | Catalog-backed resolver with bounded date interpretation, explicit timezone/building scope, clarification when ambiguous and exact validated parameters displayed with the result. |
| **P1 — deployment sizing** | Production hardware and device/system requirements remain unqualified. | The architecture correctly avoids asserting universal specifications. No named pilot source/version, asset count, event/telemetry rate, history depth, concurrency, retention target or measured host profile is present in the qualification evidence. | Complete the pilot qualification template with the real source/device/network profile; load and recovery measurements on the intended deployment topology; publish supported sizing bands and limitations. |

## Cross-cutting acceptance rule

The slice should be judged on whether it establishes reusable contracts that can serve varied building-operational needs—not on whether these two examples alone return the expected fixture rows. A new capability must remain deterministic and evidence-backed, declare its data and permission prerequisites, and fail honestly when coverage or semantics are insufficient. Chat, dashboards, reports and alerts should consume the same approved calculation/result contract.
