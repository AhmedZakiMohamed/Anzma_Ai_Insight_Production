## G3 Ollama verification note — 2026-11-22

On the fresh isolated Compose project, the API used the Compose service endpoint `http://ollama:11434` (`ollama` resolved to the project network), not a host Ollama service. `OLLAMA_MODEL` resolved to `qwen2.5:3b`, `OLLAMA_TIMEOUT` to 120 seconds, `ollama list` was empty, `/api/tags` returned `{"models":[]}`, and `/api/chat` returned HTTP 404 `model 'qwen2.5:3b' not found`. This confirms the model was not present in that isolated volume; live model inference remains **NOT TESTED**.

One-line operator fix after confirming registry access and the intended project: `docker compose --env-file .env -p "$PROJECT" -f deploy/compose/docker-compose.yml exec ollama ollama pull qwen2.5:3b`. **NOT TESTED here**; this package did not download a model or alter the Ollama volume beyond creating the empty disposable test volume.

## G4 existing-database migration note — 2026-11-22

Before running migration 013 on a pre-existing database, assign a stable operator-approved code to each null building row. Example (repeat with the real row ID/code):

```sh
docker compose --env-file .env -p "$PROJECT" -f "$COMPOSE_FILE" exec -T api \
  python scripts/ingestion_admin.py register-building --building-id <id> --building-code <stable-code>
docker compose --env-file .env -p "$PROJECT" -f "$COMPOSE_FILE" exec -T api python scripts/apply_migrations.py
```

Migration 013 was applied and rerun on disposable projects only. It raised an actionable `NotNullViolation` for null IDs `1, 2`; after codes were explicitly registered, it applied and the second runner invocation skipped it. A live/shared migration is **NOT TESTED** and was not attempted.
